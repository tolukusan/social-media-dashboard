## How to interpret evidence

- **Source verified:** implementation, configuration, migration or test exists and was inspected in this pass. Test presence is not a claim that it was rerun.
- **Historical recorded verification:** a dated repository evidence document records earlier execution; its environment and scope matter.
- **Task-supplied history:** an observation supplied by the project owner for this task that is not fully represented by committed evidence. Retained explicitly as such.
- **Live checked in this pass:** only the public read-only observations below. Private Render/provider console state and authenticated acceptance were not inspected.
- **Needs verification:** implementation/configuration exists or historical evidence is conditional, but current target-environment behaviour has not been established.

## Known limits and incomplete acceptance

- One organisation per deployment; no multi-tenancy, CRM/ecommerce, custom formula/report builder, AI recommendations or predictive analytics is established by this implementation.
- API reference is a maintained source inventory; the original planned OpenAPI/Swagger generator is not implemented in the inspected bootstrap/dependencies.
- Missing values remain unavailable. Meta report/fetch/retention windows differ, content retention is shorter, follower snapshots cannot reconstruct old counts, and partial coverage limits comparisons.
- Non-Meta account synchronization/OAuth refresh uses per-process exclusion rather than a durable cross-instance account lease. Public endpoint rate-limit maps are also process-local. Multi-instance rollout needs an explicit coordination/ingress review.
- Retention sweep depends on API uptime. Reads hide expired values immediately; older unmanaged LinkedIn campaign metrics still need a provenance/retention audit before a compliance claim. Provider policy obligations must be reviewed independently of local retention code.
- Guided KPI import drafts are not durably resumable after leaving/refreshing; older XLS requires conversion. File datasets and canonical KPI imports are separate and cannot be treated interchangeably.
- Joined view is client-side, limited to 10,000 rows/source; repeated-date alignment is by occurrence rather than aggregation, and ambiguous text dates match exactly. Browser print needs a working print window/dialog.
- Currency settings do not perform conversion; compare monetary data only after validating source meaning/currency. PDF fonts require deployment provisioning and visual QA for required glyphs.
- Free Render API sleep prevents guaranteed daily collection; Free PostgreSQL lifetime/backups and SMTP restrictions need an operator plan. Actual current private plan/version/region/deployed commits were not verified here.
- Current authenticated production role flows, SMTP inbox delivery, current provider approvals and production backup/restore drill remain separate live acceptance items. Local automated restore history does not certify production recovery.

No application behaviour was changed in this documentation task. Documentation conflicts were reconciled; implementation limitations are recorded here rather than silently repaired or treated as newly approved scope.

## Prioritised handover checklist

### P0 — before relying on the installation

- [ ] Confirm actual Render API/web deployed commits include `9762543` and `20a364f`; confirm intended database resource/schema and migration status without exposing URLs.
- [ ] Confirm `NODE_ENV=production`, same-origin proxy/callbacks, scheduler true and no deployed test flag. Confirm a continuously running API for continuous collection.
- [ ] Securely back up all current application tables/migration journal and preserve both encryption keys. Verify a restore into a new isolated target; establish ongoing backup ownership/cadence.
- [ ] Verify authenticated login/reload/logout, protected reads, roles, CSRF/Origin rejection and current report downloads with authorised accounts.
- [ ] Recheck Instagram/YouTube live values, Facebook connection/sync, LinkedIn approval and Zoho send-date report in the correct organisation. Record each provider independently.
- [ ] If self-service recovery is required, verify a real authorised inbox delivery under the deployed network/plan. Do not treat generic acknowledgement as successful email delivery.

- [ ] Assign job-age/coverage, availability, database capacity and backup alerts; review free-tier expiry/sleep limitations.
